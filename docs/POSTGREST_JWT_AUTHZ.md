# PostgREST/JWT End-to-End Authorization V1

## الهدف

تكمل هذه الطبقة اختبار RLS على مستوى SQL باختبار واجهة Supabase REST الفعلية.

يتم تشغيل Supabase محليًا في CI، ثم:
- إنشاء مستخدمين محليين وبيانات معزولة.
- إصدار JWT محلي موقع بسر بيئة Supabase المحلية.
- إرسال طلبات HTTP إلى PostgREST.
- التحقق من القراءة والكتابة والحذف عبر RLS كما يراها التطبيق.

## الحالات

- API-001: المستخدم يرى مستنداته فقط.
- API-002: lookup مباشر لمستند مستخدم آخر يعيد قائمة فارغة.
- API-003: PATCH لمستند مستخدم آخر لا يعدل شيئًا.
- API-004: PATCH للمستند المملوك ينجح.
- API-005: INSERT لمستند مملوك للمستخدم ينجح.
- API-006: INSERT باسم مالك آخر يُرفض.
- API-007: عدم وجود DELETE policy يمنع حذف المستند حتى من مالكه.
- API-008: anon لا يرى بيانات المستخدمين.
- API-009: المستخدم لا يستطيع INSERT مباشرة في document_versions المخصص لمسار الخادم/Worker.
- API-010: server credential يحتفظ بالوصول الإداري المطلوب.

## الأمان والعزل

- لا يتم استخدام مفاتيح مشروع مستضاف.
- كل المفاتيح وJWTs مصدرها Supabase المحلي داخل Runner.
- لا تُطبع القيم السرية في التقرير.
- بيانات الاختبار تُحذف في finally حتى عند فشل assertion.

## حدود V1

لا تختبر هذه الطبقة واجهة نَضِيد Next.js نفسها أو cookies الخاصة بـSSR. هذه طبقة Supabase API authorization مباشرة.
